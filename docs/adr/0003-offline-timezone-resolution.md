# 0003 — Offline timezone: polygons → boxes → longitude fallback

Date: 2026-07-06 (boxes), 2026-07-12 (polygons), 2026-08-02 (dual resolution) ·
Status: **Accepted**

## Context
The clock must derive local time (incl. DST) from GNSS coordinates with **no
network**. Full IANA border data is far too large for an MCU; a naive
longitude formula gets whole countries wrong.

## Decision
Three layers, first hit wins:
1. **Polygons**: real IANA borders from timezone-boundary-builder,
   simplified to int16 centidegrees, smallest-area-first so enclaves win.
   Generated by `tools/gen_tz_polys.py`, hand-refinable in
   `tools/tz_polygon_editor.html`. **Two resolutions of the same map**,
   picked at compile time by flash size: the J20 (1 MB) includes
   `TimezonePolyDataFine.h` (eps 0.015° ≈ 1.7 km worst-case, 404 zones /
   927 polygons / 56k vertices, ~250 KB — close to both the 1.1 km int16
   quantization floor and the uint16 vertex-index ceiling); the J19
   (512 KB, ~85 % full) keeps the coarse `TimezonePolyData.h`
   (eps 0.20°, ~383 zones, ~57 KB).
2. **Boxes** (`kZones[]`, 214): hand-curated rectangles, exceptions-first
   (Arizona, Saskatchewan, Kaliningrad, …) — also the fallback data set.
3. **Longitude**: `round(lon/15)` → whole-hour offset, no DST. Every
   coordinate resolves.
Zones carry **POSIX TZ strings** evaluated at runtime by a host-unit-tested
parser (`Timezone.*`, `pio test -e native`).

## Consequences
- Correct offset + DST for essentially every populated place, offline.
- POSIX strings with non-`M` DST rules are unsupported by the evaluator —
  the generator sanitizes them to fixed offsets (found via Morocco).
- Border precision is ~km-level (simplification); offsets rarely differ
  across a border anyway. Manual GMT-ladder override exists in the menu.
